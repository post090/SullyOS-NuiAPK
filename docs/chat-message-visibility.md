# 首页或通知有消息，私聊里却没有

2026-09-11 排查记录。两个反馈只有截图，以下是代码与复现能确认的缺陷，不代表已经确认反馈设备上的唯一原因。

## 已修正

- 首页消息卡原来只排除 system，会预览 `source: date / call / story_theater_memory` 和主动消息的内部提示；私聊则排除这些内容。正文未必带来源格式，不能靠文案判断它属于哪个界面。桌面消息卡现在复用 `utils/chatMessageVisibility.ts` 的私聊范围。
- Chat 原来先取最近 N 条，再过滤来源。连续大量见面/通话记录会占满窗口，真正的聊天仍在数据库里，却没有被取出来。`DB.getRecentMessagesWithCount` 现在支持在游标收集时筛选，只有可展示的消息占用数量额度。普通主动回复、通话后的私聊回信和评分卡保留原有显示规则。
- 默认首页的消息预览不再使用受记忆处理水位影响的上下文查询。界面读取与模型上下文截断是两件事，本次不重置记忆或迁移聊天数据。
- `saveScheduledMessage` 原来发起写入就返回；`saveMessage` 原来在单条请求成功时返回，事务仍可能随后回滚。现在等事务提交，错误或中止会拒绝 Promise，调用方不会把这种失败当保存成功继续安排通知或销掉定时任务。定时任务删除也等待提交。

手游/电子宠物桌面的消息预览同样排除其他界面来源；等级与互动统计维持原有取数方式。

## 定时通知的边界

`chatPrompts.ts` 的本地定时指令允许角色自行安排未来留言，不要求用户先手动配置主动消息。`chatParser.ts` 保存任务后，可以在原生环境安排系统闹钟通知；真正的聊天记录由 OSContext 的定时轮询补入。正在见面或通话（含挂起通话）时会暂缓该角色的投递。

因此系统通知出现不等于聊天记录此时已经落库。只有通知截图、没有平台/版本/日志，无法认定它就是传统定时消息、主动消息 1.0 或 2.0。“找回没收到的消息”检查的是 2.0 云端补收账本，不能据此排除其他通道的问题。本次未修改云端补收协议，也不能恢复已经丢失且没有留存副本的内容。
